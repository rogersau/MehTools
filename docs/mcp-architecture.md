# MCP architecture

The dependency direction is `MCP transport -> DiagnosticAccess -> Core contracts -> existing diagnostics`. The standalone .NET 10 Windows host references `JamesTools.Core`; Core has no SDK or transport dependency. The WPF app configures enablement, shows verified host status and copies connection commands using the [configuration contract](../src/JamesTools.Mcp/CONFIGURATION.md). The client or terminal launches the host; the desktop does not start it automatically or implement a second diagnostic server. Publishing includes `tools/mcp/MehTools.Mcp.exe` and its dependencies.

## Shared v1 domain boundary

`src/JamesTools.Core/Mcp/Contracts.cs` contains the frozen transport-independent records plus `IDiagnosticBackend` and `IDiagnosticSessions`. Inventory, metric, event, finding, health, game, session and history records cross this boundary as typed data. UTC timestamps, schema version 1, units, explicit availability and nullable readings keep presentation/client behavior independent of hardware-provider details. A client must not substitute zero for missing evidence. Finding explanations are hypotheses with confidence and next checks, not unconditional diagnoses.

`WindowsDiagnosticBackend(string appDataDirectory)` adapts the existing inventory, hardware telemetry, game detection, Windows events and diagnostic/report functionality. It owns its hardware/provider resources and is disposable. `DiagnosticSessionService(IDiagnosticBackend, string storageDirectory)` owns bounded asynchronous collection and history; it is asynchronously disposable. The storage directory is an application-selected path, never an MCP request parameter. Shared interfaces make deterministic tests possible without exposing fixtures in a release host.

## Host and transports

`DiagnosticTools` uses official SDK tool attributes and typed arguments/return values. `ToolRegistration` supplies strict serialization and generated JSON schemas while preserving the frozen inventory dictionary's nullable values. Nullable numeric values/end times/statistics remain explicit JSON nulls so successful output conforms to its advertised schema. `DiagnosticResources` serializes the same domain records. `DiagnosticAccess` performs admission control, validates identifiers/ranges/durations, applies deadlines, bounds serialized output and maps failures to safe errors. It retains only the latest report for this host. There is no shell tool, arbitrary query engine, file browser or user-selected write destination.

The stdio host reads newline-delimited MCP frames and reserves stdout for protocol responses. The client owns the child process. EOF/disconnect must terminate capture and dispose services promptly. HTTP uses ASP.NET Core and the SDK Streamable HTTP transport at `/mcp`. Explicit enablement, opt-in HTTP startup, constant-time bearer-secret verification, exact Host/Origin checks, 64 KiB request bounds and 1 MiB output bounds sit in front of diagnostic work. Loopback is the default. Nonloopback requires TLS. Host-level configuration and runtime status are separate from protocol payloads; tokens are read from environment variables and excluded from status.

The official SDK handles initialization and JSON-RPC framing/tool/resource dispatch. It does not replace domain validation: reflected schema types alone do not establish duration ranges, identifier restrictions, UTC-only times or bounded query windows. Errors must not disclose exception messages, internal file paths, stack traces or credentials.

## Sessions and persistence

Session start returns an ID promptly. A background collector samples existing telemetry according to the selected profile/interval. Session reads return at most 40 snapshots (6 KiB each) plus 64 aggregate series, with a 300 KiB record budget; long-running capture retains aggregates without returning an unbounded array. Live telemetry has a separate 128-metric/96 KiB budget so session prioritization does not discard useful live CPU/memory readings. Stop is idempotent. Disposal cancels active captures. Unsupported readings stay null and do not contribute zeroes to averages. Names and units identify a statistical series together. History queries use UTC windows, bounded filtering and an optional preceding equal comparison window.

Session persistence validates schema, IDs, timestamps, collection sizes, status/value consistency and byte budgets. The service adds an `mcp-sessions` child to its application-selected storage root. It shares a four-recording limit and retains at most twelve sessions for seven days, with a 32 MiB ceiling including staging/backups. Session files are application-managed records, not a general filesystem API. Partial, corrupt, oversized or unsupported-version persisted data must be reported or rejected safely. Interrupted work must not reappear as an actively recording capture after restart. A generic session has no scoped game/process identity in v1, so it does not silently start PresentMon or claim frame timing.

## Test design

`tests/JamesTools.Mcp.Tests` is a framework-free executable, matching the repository's test convention. It references the production host and official MCP client package. Test subprocesses register deterministic `IDiagnosticBackend` fixtures through `McpHost.AddDiagnostics`; `McpHost.BuildStdioHost` supplies real production stdio framing and dispatch. Test-only command switches belong to the test executable, never the production host. Fixtures include explicit unsupported/permission/unavailable/failure sensors, null statistics, installed DLLs with unknown runtime status, slow collectors, oversized data and backend failure.

The protocol suite initializes the official client, verifies all ten tools and advertised input/output schemas, invokes every tool, validates structured content against its advertised JSON schema, discovers/reads resources, rejects invalid/unknown requests, and checks connection usability after errors and clean disconnection. HTTP tests use the real production security pipeline for missing/wrong bearer tokens, Host/Origin rejection and oversized requests. HTTPS tests exercise PFX loading, TLS, authentication rejection and official-client initialization/invocation with an ephemeral certificate pinned only by that client; no global trust changes are made. Session tests use the production service with deterministic collectors to verify cancellation, concurrency, bounds and persistence. Response-size checks include the serialized MCP result, not just the domain object. A maximum-duration persisted fixture fills all 40 retained sample slots to exercise the encoded response budget. Remote nonloopback/Tailscale deployment is not covered.

The separate `--hardware` mode launches the real Windows host. It verifies inventory/live telemetry/diagnostics and start/get/stop through official clients rather than calling Windows collectors directly. Hardware observations are machine-dependent: tests assert honest availability/null handling and print observed statuses. A fixture success is not evidence that a particular physical sensor/driver was exercised. Tests do not alter power plans, game files or recording configuration. Only test-managed config/session artifacts and diagnostic history are written.

Run the commands in [mcp.md](mcp.md#validation-commands). A successful build does not establish end-to-end transport or hardware correctness; use the executable's actual PASS/FAIL output and reported hardware observations. No commit, push or installation is required to run the harness.
